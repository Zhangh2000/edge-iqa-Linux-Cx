# 简历项目表述

## 可直接放入简历

### Linux 边缘端气象图像质量检测与异常告警系统

**项目简介：** 面向气象卫星图像传输与边缘侧巡检场景，基于 C++17 和 OpenCV 设计图像质量检测系统，支持参考图/待测图离线评估、视频文件或摄像头流式检测以及 TCP 图像传输。系统输出 MSE、PSNR、SSIM、亮度、清晰度、FPS 和处理延迟，通过连续帧状态机产生异常告警，并将离线及逐帧结果写入 CSV。使用 Ubuntu 24.04 ARM64 Docker 完成 Linux 构建验证。

**个人角色：** 独立完成需求拆分、系统架构、核心算法、C++ 模块开发、CMake 构建、Linux ARM64 环境搭建、数据处理、测试验证和项目文档。

**技术栈：** C++17、Linux/Ubuntu、GCC、CMake、OpenCV、`std::thread`、Mutex/Condition Variable、Socket/TCP/IP、CRC32、CSV、Docker ARM64、Git。

**项目重点与难点：**

- **图像质量评估与数据集构建：** 实现 MSE、PSNR 和 11x11 高斯窗口灰度 SSIM；对 FY-4B AGRI 气象图像截取固定 2048x2048 ROI，确定性生成 3 档高斯噪声、3 档高斯模糊和 3 档 JPEG 压缩样本，自动生成 90 对清单并实现批处理，完成 90/90 回归。
- **实时指标与异常告警：** 使用 `cv::VideoCapture` 统一视频文件和摄像头输入，逐帧计算灰度均值亮度、拉普拉斯方差清晰度、处理延迟和平滑 FPS；设计 `UNASSESSED/NORMAL/WARNING/ALARM` 状态机，采用连续帧触发和恢复滞回抑制阈值附近的状态抖动。
- **多线程任务调度：** 使用 `std::thread`、互斥锁和条件变量实现线程安全有界队列，将采集与计算解耦；文件输入采用阻塞背压保证完整性，摄像头输入采用丢弃最旧帧策略限制实时延迟，并统计采集、处理、丢帧和最大队列深度。
- **TCP/IP 图像传输：** 基于 Linux Socket 设计 `EIQ1` 应用层分帧协议，使用固定 16 字节包头携带消息类型、负载长度和 CRC32；实现循环收发以处理 TCP 短读短写，客户端 JPEG 编码、服务端内存解码并返回质量与告警结果。
- **工程化与跨环境构建：** 将指标、I/O、失真、告警、队列、网络和 CSV 按职责拆分，使用 CMake 管理核心静态库与 5 个命令行程序；分别维护 macOS `build/` 和 Linux `build-linux/`，在 Ubuntu 24.04 ARM64 Docker 中使用 GCC/OpenCV 完成构建及 headless 视频验证。
- **数据与验证：** 使用国家卫星气象中心 FY-4B 数据，建立可追溯元数据清单；构造“正常 + 暗化模糊”气象序列，验证状态从 `NORMAL` 经 `WARNING` 进入 `ALARM`；完成异常路径、CRC32 标准向量和 TCP 回环测试。

## 一分钟项目介绍

这个项目解决的是边缘端接收到的气象图像可能因噪声、模糊、压缩或链路异常而质量下降的问题。我先实现离线全参考评价和 90 对数据集批处理，再把输入扩展为视频流，计算不依赖参考图的亮度和拉普拉斯清晰度，并通过连续帧状态机告警。为了符合 Linux 边缘系统的数据流特点，我用有界生产者-消费者队列解耦采集和计算，同时设计了带长度和 CRC32 的 TCP 图像协议。项目在 macOS 完整验证，并在 Ubuntu ARM64 Docker 中完成 Linux GCC/OpenCV 构建和 headless 视频验证，目前尚未宣称树莓派和真实摄像头实机部署。

## 十分钟面试展开顺序

1. **为什么做：** 本科图像质量评价原型偏离线，希望改造成可运行于 Linux 边缘环境、包含视频流和网络链路的 C++ 系统。
2. **数据和指标：** 说明 FY-4B 来源、固定 ROI、9 类失真、MSE/PSNR/SSIM 的适用条件和局限。
3. **实时链路：** 解释 `VideoCapture -> 有界队列 -> 指标 -> 告警 -> CSV/Overlay`。
4. **最大难点：** TCP 无消息边界、多线程停止与背压、阈值抖动、macOS/Linux 构建目录隔离。
5. **为什么这样设计：** 文件和摄像头对丢帧的目标不同；CRC 用于完整性检测；状态机用连续帧降低误报；模块化便于后续替换质量算法。
6. **验证证据：** 90/90、正常/退化气象序列、20/20 无丢帧、CRC 标准向量、TCP 回环和 Linux ARM64 build。
7. **当前边界：** 无树莓派实机、无真实 V4L2、无 TLS、多客户端和 Edge AI；明确后续工作而不虚构结果。

## 高频追问口径

**为什么不用 Python？** 目标是练习 Linux/C++ 工程、线程和 Socket，并为资源受限边缘设备保留较低运行时开销与明确的资源控制；Python 更适合快速算法实验，但不是本项目的工程目标。

**为什么用 OpenCV？** 它提供成熟的图像解码、颜色转换、滤波、视频输入和 JPEG 编解码，项目将精力集中在质量算法、数据流和系统边界，而不是重复实现编解码器。

**为什么用多线程？** 采集属于 I/O，指标属于计算，有界队列可以解耦节拍并建立内存上界。项目不把“线程更多”当作吞吐保证，而是用不同背压策略满足文件完整性和摄像头低延迟。

**为什么 TCP 还要自定义协议？** TCP 只提供可靠有序字节流，没有消息边界。必须发送 Magic、类型和长度才能恢复完整消息；CRC32用于检测负载损坏。

**为什么 CSV？** CSV 是轻量、可审计且跨工具的结果交换格式，可用 Excel、Python 或命令行分析；它适合实验和日志导出，但高并发生产系统可换为数据库或结构化日志。

**为什么没有直接算视频 SSIM？** SSIM 是全参考指标，实时现场通常没有与当前帧严格配准的无失真参考图。当前实时链路使用亮度和清晰度，离线数据验证使用 MSE/PSNR/SSIM；若有参考序列，还需先做时间与空间配准。

**Docker 能代表树莓派吗？** 只能验证 ARM64 Linux 用户态、GCC 和依赖兼容性，不能代表摄像头驱动、真实 CPU 性能、温度、功耗和长期稳定性，所以简历不写“树莓派实机部署”。
